Genesis Group is building its DevSecOps practice from the ground up. You are being evaluated for the senior engineering role that will own infrastructure, pipelines, reliability, and security across three companies — Genesis, Puretech Digital, and NetImpact.

Part 1  —  Terragrunt IaC Architecture
40 Marks  |  Estimated Time: 1.5 – 2 Days
This is your strongest domain — and the bar is set accordingly. We are not evaluating whether you can write Terraform. We are evaluating whether you design infrastructure the way a senior engineer should: safe, composable, auditable, and drift-resistant.

1.1  Repository & Module Structure  [10 Marks]
Organise your IaC using Terragrunt. A flat main.tf scores zero for structure regardless of content quality. The directory hierarchy must reflect real-world best practice.

Required structure — implement all of the following:

  infrastructure/
    ├── terragrunt.hcl                  # Root config: remote state, provider, common inputs
    ├── modules/
    │   ├── iam/                        # IAM roles, policies, OIDC provider
    │   ├── compute/                    # Lambda / Cloud Run resource
    │   ├── networking/                 # VPC, subnets, security groups (if using EC2/ECS)
    │   └── observability/              # CloudWatch log group, dashboard, alarms, SNS
    └── environments/
        ├── dev/
        │   ├── terragrunt.hcl          # Inherits root; dev-specific vars
        │   ├── iam/terragrunt.hcl
        │   ├── compute/terragrunt.hcl
        │   └── observability/terragrunt.hcl
        └── prod/
            └── ...                     # Identical structure, different var values

Each module must have a README.md generated by terraform-docs or written manually. It must document every input variable, every output, and the purpose of the module in two sentences.

1.2  Security & Compliance Standards  [15 Marks]
These are non-negotiable. Every item below is checked during evaluation.

•	OIDC authentication for GitHub Actions: the pipeline must assume an IAM role via OIDC — no AWS_ACCESS_KEY_ID or AWS_SECRET_ACCESS_KEY in GitHub Secrets. The OIDC provider and IAM role must be Terragrunt-managed, not created manually in the console.
•	Least-privilege IAM: the Lambda execution role and the GitHub Actions deployment role must have only the permissions the code actually exercises. Run aws iam simulate-principal-policy against your role and include the output in your repo under reports/iam_simulation.txt.
•	No hardcoded values: account IDs, region strings, ARNs must be variables or data sources. Run grep -r '<your_account_id>' infrastructure/ — it must return zero results.
•	Secrets from AWS Secrets Manager or SSM Parameter Store: if your application uses any secret value (even a dummy API key), it must be fetched at runtime, not baked into the Terraform configuration or the container image.
•	S3 state bucket: versioning enabled, server-side encryption enabled, public access blocked, access logging to a separate bucket.
•	Resource tagging: every resource must carry at minimum — Environment, Project, ManagedBy=terragrunt, Owner.

1.3  Checkov Scan & Policy Enforcement  [10 Marks]
Run Checkov against your entire infrastructure directory. Include the full JSON report at reports/checkov_report.json.

  pip install checkov
  checkov -d infrastructure/ --framework terraform --output json > reports/checkov_report.json

Requirements:
•	Zero CRITICAL findings on resources you authored. Findings on provider-generated resources or known false positives are acceptable if annotated.
•	Any Checkov skip comment (# checkov:skip=...) must include a written justification in the same line. 'Not applicable' is not a justification.
•	Add Checkov as a pipeline stage (see Part 2, Stage 10) — it must run on every pull request and block on CRITICAL findings.

Bonus  +5 marks
• Write an OPA/Conftest policy that enforces at least two Genesis Group-specific guardrails beyond what Checkov covers by default. Examples: 'all Lambda functions must have a dead_letter_config', 'no S3 bucket may have a name containing the word "public"', 'all CloudWatch alarms must have an SNS action configured'.
• Show the policy blocking a non-compliant resource and the compliant version passing. Commit the .rego or conftest YAML to infrastructure/policies/.

1.4  Drift Detection Design  [5 Marks]
Terraform drift — real resources diverging from declared state — is a common production problem. Write a 400-word design note (committed as docs/drift-detection-design.md) covering:
•	How you would detect drift in a live environment. What would the automated detection mechanism be? How frequently would it run?
•	What your response policy is when drift is detected: who is notified, what is the SLA for remediation, and when (if ever) is drift accepted and the state updated to match reality?
•	How Terragrunt's architecture specifically helps — or doesn't help — with drift compared to vanilla Terraform workspaces.
This is a design document, not implementation. It will be evaluated on clarity of thinking, not on whether you've built the mechanism.
 
Part 2  —  Secure CI/CD Pipeline
40 Marks  |  Estimated Time: 1 – 1.5 Days
Build a complete, working pipeline for a sample application. The application is trivial — a three-endpoint HTTP API in Python or Node.js. The pipeline is the deliverable.

2.1  The Application
Build a minimal API with three endpoints. Keep the application simple — the engineering is in the platform, not the code.

Method	Endpoint	Behaviour
GET	/health	Returns {"status": "ok", "version": "1.0.0", "env": "<environment>"}
POST	/events	Accepts JSON body, validates required fields, returns 201 with the event ID
GET	/events/{id}	Returns the event by ID or 404 with a structured error body

Plant two security flaws — mandatory   — pipeline must catch both
• Flaw 1 (secrets): Hardcode a fake credential as a string literal in the source code — e.g., DB_PASSWORD = 'genesis-db-p4ss'. Your pipeline's secret scanner must catch it and block the run. Document the flaw and its detection in your README.
• Flaw 2 (code quality): In your POST /events handler, log the raw request body without sanitisation — a pattern that leaks PII in production logs. Your SAST tool must flag it. Document this too.
• Fix both flaws. Show a failed pipeline run (security gate blocking), then a full green run after the fix. Both screenshots are mandatory.

2.2  Pipeline Stages
Implement in GitHub Actions. All 12 stages are mandatory. The pipeline runs on every PR (stages 1–10) and deploys only on push to main (stages 11–12).

#	Stage	Tool	Gate?	Evidence Required
1	Secret Scanning	Gitleaks  (gitleaks/gitleaks-action)	YES	Screenshot of blocked run on planted secret
2	Dependency Audit	pip-audit  or  npm audit  or  Snyk	YES	Report exported as pipeline artifact
3	SAST	Semgrep  (returntocorp/semgrep-action)	YES	SARIF report uploaded to GitHub Security tab
4	Unit Tests + Coverage	pytest + pytest-cov  or  jest --coverage	YES	Coverage ≥ 75%; badge in README
5	Docker Build	docker buildx  (multi-stage: builder + runtime)	NO	Image built and tagged with git SHA
6	Image Vulnerability Scan	Trivy  (aquasecurity/trivy-action)	YES	CRITICAL findings block; report as artifact
7	SBOM Generation	Syft  (anchore/sbom-action)	NO	CycloneDX JSON attached as artifact
8	Image Signing	Cosign  (keyless OIDC signing)	NO	Signature stored in ECR alongside image
9	IaC Lint	tflint  on  infrastructure/		
YES	Zero errors; warnings documented			
10	Checkov Scan	checkov  on  infrastructure/	YES	CRITICAL findings block; report as artifact
11	Terragrunt Deploy	terragrunt apply  (dev environment)	YES	Deploy only on main; smoke test follows
12	Smoke Test	curl  or  pytest  against live endpoint	YES	GET /health returns 200; pipeline fails otherwise

2.3  Pipeline Engineering Standards
Beyond running the stages — the pipeline itself must demonstrate senior engineering judgment:

•	Fail fast and ordered: secret scanning (Stage 1) must run before build (Stage 5). If Stage 1 fails, Stages 2–12 must not start. Use needs/depends_on correctly — show this in the YAML.
•	OIDC only: the Terragrunt deploy stage must use aws-actions/configure-aws-credentials with role-to-assume. The pipeline YAML must not contain AWS_ACCESS_KEY_ID anywhere — including in comments.
•	Environment-scoped secrets: production credentials (if you add a prod environment) must use GitHub Actions Environments with required reviewers — not repository-level secrets.
•	Pipeline as code: the .github/workflows/ directory must itself be subject to change review. Add a CODEOWNERS file requiring at least one senior engineer review on any workflow file change.
•	Reusable workflows: extract the security scanning stages (1–4) into a reusable workflow (.github/workflows/security-scan.yml) that the main pipeline calls. This models how a platform team would share standards across multiple repositories.

2.4  Evidence Required for Part 2
What to submit
• Screenshot or short clip of a FAILED pipeline run — Gitleaks or Semgrep blocking on the planted flaw. Label which flaw was caught.
• Screenshot of a full GREEN pipeline run — all 12 stages passing, all artifacts uploaded.
• GitHub Actions run summary showing: Trivy report, SBOM file, and Checkov report visible as downloadable artifacts.
• The .github/workflows/ YAML files — committed, commented, and readable.
• CODEOWNERS file in the repository root.
• README section titled 'Pipeline Architecture' — explain the fail-fast ordering, the OIDC approach, and the reusable workflow pattern. Three short paragraphs.
 
Part 3  —  Observability, SLOs & Runbooks
30 Marks  |  Estimated Time: 0.5 – 1 Day
This part deliberately sits in a gap area. The goal is not perfection — it is to show that you can define reliability targets, connect them to operational behaviour, and write the human process around them.

3.1  CloudWatch Dashboard via Terraform  [10 Marks]
Provision a production-quality CloudWatch dashboard for your Lambda function entirely via Terraform — inside modules/observability. No console clicks.

Required panels — implement all six:
•	Invocation count (requests/min) — traffic signal
•	Error rate % ((errors / invocations) × 100) — the most important signal
•	Duration P50 and P99 (milliseconds) — not just average; latency distribution matters
•	Throttle count — free tier canary: if Lambda throttles, you are over limits
•	Concurrent executions — shows scaling behaviour
•	One custom metric: emit a CloudWatch metric from your POST /events handler counting events by type. Show it on the dashboard. Use PutMetricData via the AWS SDK — not a log filter.

Include a screenshot of the live dashboard with real data (call the endpoints a few times after deploy). The dashboard must show at least 15 minutes of data.

3.2  Alerting with Operational Context  [8 Marks]
Create two CloudWatch Alarms in Terraform — both in modules/observability, both wired to an SNS topic that delivers to your email.

•	Alarm 1 — Error Rate: trigger when error rate > 5% over a 5-minute window. Alarm must have a descriptive AlarmDescription that includes: what this metric measures, what a breach means in operational terms, and the runbook URL.
•	Alarm 2 — Duration Anomaly: trigger when P99 duration exceeds 3× the 7-day P99 baseline (use a metric math expression). This tests whether you know how to write a relative threshold, not just an absolute one.

Prove both alarms work: temporarily force a failure condition (e.g., introduce a deliberate error in the handler), show the alarm transitioning to ALARM state in a screenshot, then recover.

3.3  SLO Definition & Error Budget Policy  [12 Marks]
Define a Service Level Objective for your API. This section is scored on reasoning quality, not on whether you've run an SLO platform.

Create slo/genesis-api-slo.yaml. A template is provided — fill in every field based on your actual deployment:

  service:          genesis-events-api
  environment:      dev
  
  sli:
    type:           availability
    measurement:    (successful_invocations / total_invocations) * 100
    datasource:     CloudWatch — Lambda Errors + Invocations metrics
    query:          <paste your CloudWatch Metrics Insights query here>
  
  slo:
    target_percent: <your choice — justify it below>
    window:         30d
  
  error_budget:
    allowed_downtime_minutes:    <calculated>
    burn_rate_alert_threshold:   <at what burn rate do you page?>
    current_burn_rate:           <measured after running for ≥ 1 hour>
  
  policy:
    at_50_percent_budget_consumed:   <what happens — alert, meeting, nothing?>
    at_75_percent_budget_consumed:   <what happens>
    at_100_percent_consumed:         <what happens — deployment freeze, incident?>
    review_cadence:                  <how often and who attends>
  
  owner:            <your name>
  last_reviewed:    <date>

After the YAML, write docs/slo-rationale.md (300–400 words) answering:
•	Why did you choose that SLO target — what data informed it? (Your Lambda will have some real invocation data after testing.)
•	What does a 'burn rate alert threshold' mean — explain the concept in plain English as if explaining it to a developer who has never heard of SLOs.
•	What would you change about this SLO definition after one month of real production data? What would you watch for?

Why this section is scored on reasoning not tooling
• Datadog is the Must Have platform in this role. You do not have it yet. That is fine — the SLO section tests whether you understand the engineering discipline behind SLOs, which transfers to any tooling.
• The burn rate concept is the dividing line. Anyone can set a CloudWatch alarm at 5% error rate. Someone who understands burn rate understands why that alarm fires too late.
 
Part 4  —  Disaster Recovery Design
10 Marks  |  Estimated Time: 0.5 Day  |  Written deliverable
DR is absent from your CV. This part does not require you to build a DR environment — it requires you to think like an engineer who designs one. The deliverable is a written DR design document for the environment you built in Parts 1–3.

The scenario
• Genesis Group's CTO asks you: 'If the AWS region we're deployed in has a full outage tonight, what is our recovery plan? How long will it take and how much data will we lose?'
• You have not yet defined RTO or RPO for this service. You have 24 hours to produce an answer.

4.1  DR Design Document  [10 Marks]
Write docs/dr-design.md. It must cover all of the following — use sub-headings, not prose paragraphs:

1.	Current state inventory: what exists in your deployed environment (Lambda, ECR image, CloudWatch config, state files) and where it lives. What would be lost in a regional failure?
2.	RTO and RPO targets: propose specific targets for this service and justify them. The justification must reference the business context (an internal operations tool vs. a customer-facing SaaS has different tolerances). Show the calculation: at 99.5% SLO, what is the monthly allowed downtime?
3.	Recovery strategy: for each component in your inventory, state the recovery mechanism. Lambda code: redeployed from ECR (which must be cross-region replicated — is it?). Terraform state: recovered from S3 (which must have cross-region replication enabled — does it?). Application data: your Lambda is stateless, but if it weren't, what would you do?
4.	DR runbook: write a numbered, command-level recovery procedure. Not prose — numbered steps, with the actual CLI commands or console actions at each step. Someone who has never seen this environment before should be able to execute this runbook. The runbook must include a validation step: how do you confirm recovery was successful?
5.	Gap analysis: what does your current free-tier architecture not yet support for production-grade DR? Name the specific gaps (cross-region replication not configured, Route 53 health checks not set up, etc.) and what you would add with a real infrastructure budget.

How this is scored
• The RTO/RPO calculation is the technical litmus test. If you say 'RTO is 4 hours' without showing how you arrived at that number or what architectural choices achieve it, the marks are not awarded.
• The runbook must have actual commands. A recovery runbook that says 'deploy the Lambda function' without the aws lambda or terragrunt apply command is not a runbook.
• The gap analysis is worth as many marks as the runbook — identifying what's missing is as important as describing what's there.
